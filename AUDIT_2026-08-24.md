# Internal audit of commit `5b1b779`

A read of the whole trust boundary — `server/src`, `firestore.rules`, `lib/` —
looking for defects rather than responding to someone else's list. Every finding
below was reproduced before it was changed, and every claim about what the code
did is a claim about code that was read, not inferred.

**The starting point was green**, which is why the findings are where they are.
`flutter analyze` was clean, 482 Dart tests passed, 279 server tests passed, and
all 222 `rules_test` cases passed against the emulator. Nothing an existing test
covers was broken. The defects that survive a suite that good live in the seams
the suite does not cross: a wire key nobody asserts on, a client-side bound that
`firestore.rules` enforces and the form does not, a truncation that produces a
string one layer down refuses.

## F1 — the weekly claim quota always read as unused (F6.4)

**Severity: medium. The one finding with a user-visible functional consequence.**

`ClaimService.fetchQuota` parsed the count out of `body['approvedThisWeek']`.
The server has never sent that key. `claimQuotaStatus()` in
`server/src/claims.js` returns `{ weekKey, used, limit, remaining, claimAward }`,
and the route spreads it into `{ ok: true, ... }` — the count is **`used`**.

So `wireInt(body['approvedThisWeek'])` was always null, always fell back to the
`?? 0`, and `ClaimQuotaStatus.remaining` was therefore always the full
allowance. `isExhausted` could never be true. The banner at the top of
`claim_submit_view.dart` told every Champion "3 claims left this week", whatever
they had actually used.

What that costs is exactly what §7.4 says the endpoint exists to prevent: the
quota is enforced inside `approveClaim`, so a Champion at their limit chose an
action, photographed it, uploaded the evidence and submitted — and found out
days later, from a review that failed with "This user has reached the weekly
limit of 3 approved claims". The endpoint's own docstring says it is read
"before composing a claim, so someone at their limit is told before they
photograph something rather than after". It was being read and then discarded.

**Fixed** in `lib/services/claim_service.dart`. The parsing moved out of the
service into `ClaimQuotaStatus.fromJson`, which reads `used`, and the whole
class comment now names the server function the contract comes from. Splitting
it out is the point as much as the key is: `fetchQuota` needs a Firebase session
to build its headers, so inline parsing could not be tested at all, which is why
a key that never existed survived. `test/claim_quota_status_test.dart` pins the
contract in six cases, including a lowered mid-week limit and a damaged body.

## F2 — an over-long tag made the whole product write fail with no reason

**Severity: medium.**

`normalizeTag` in `lib/core/product_taxonomy.dart` stripped edge dashes and
*then* truncated at 40 characters:

```dart
final trimmed = cleaned.replaceAll(RegExp(r'^-+|-+$'), '');
return trimmed.length > 40 ? trimmed.substring(0, 40) : trimmed;
```

The cut lands wherever character 41 happens to be. When that is the separator
between two words, the result ends in a dash — and both `validTag` and
`validSearchToken` in `firestore.rules` require
`^[a-z0-9]+(-[a-z0-9]+)*$`. Reproduced with the tag
`handmades recycleds shoppings luggagess carrier`, which normalises to
`handmades-recycleds-shoppings-luggagess-`.

The tag and the search token derived from it are written in the same document
as the listing, so one such tag failed `createProduct`/`updateProduct` entirely
with a bare `permission-denied` — a rules refusal cannot say which of a dozen
bounds it was, and the seller console offered nothing to correct. It is
reachable today: the tags field is free text split on commas with no length
limit of its own.

**Fixed** by stripping trailing dashes again *after* the truncation. Two tests
added to `test/core/product_taxonomy_test.dart`: one on the exact 9/9/9/9 word
layout that lands the cut on a separator, and one asserting that every token
`searchTokensFor` can emit satisfies the pattern the rules check it against —
the second is the one that would have caught this, and the general shape is
worth more than the specific case.

## F3 — client validators did not mirror the maxima `firestore.rules` enforces

**Severity: medium on the registration path, low elsewhere.**

The rules pin an exact length on every stored string. The forms checked only the
minima:

| Field | Rule | Form checked |
|---|---|---|
| `users.name` | 2–80 | ≥ 2 |
| `sellerApplications.businessName` | 2–120 | ≥ 2 |
| `sellerApplications.description` | 20–1000 | ≥ 20 |
| `sellerApplications.reason` | 10–500 | ≥ 10 |

A write that breaks one is refused with a `permission-denied` that names no
field. On the seller-application and rejection paths that is an unexplained
failure. **On registration it is worse than a refusal**: `AuthController.signUp`
creates the Auth account first, and its rollback — correct in itself — deletes
the account when the profile write fails. So a name over 80 characters produced
a generic "try again", left nothing behind, and reproduced identically on every
retry.

**Fixed** in `lib/core/validators.dart`. A `TextLimits` class holds the four
pairs with the same "duplicated in `firestore.rules`, change both" contract
`ProductLimits` already documents for the marketplace; `validateName` gained the
ceiling; `validateMinLength` gained an optional `maximum` that reports how far
over the text runs. The seller-application fields and the shared rejection
dialog now carry matching `maxLength` caps, so the state cannot become invalid
in the first place. `test/validators_test.dart` covers the new bounds and pins
the constants against the rules.

## F4 — four screens still printed raw exceptions at the user

**Severity: low.**

`lib/core/network_errors.dart` exists for this and says so at length; a comment
in `seller_application_view.dart` calls itself "the last raw `$error` surface in
`lib/views/`". It was not. Four snackbar paths still interpolated the exception
directly, and all four can receive a `FirebaseException`, which renders as
`[cloud_firestore/permission-denied] Missing or insufficient permissions.`:

- `seller_products_view.dart` — delisting a listing (a bare Firestore write)
- `product_detail_view.dart` — adding to the cart
- `admin_appeals_view.dart` — recording an appeal decision
- `appeal_form_view.dart` — the fallback beside its handled `permission-denied`

**Fixed** by routing all four through `friendlyErrorMessage`, which passes the
app's own exception types through unchanged and translates the vendor codes.

## F5 — the appeal answer dialog computed its validation and never showed it

**Severity: low.**

`_AnswerDialog` in `admin_appeals_view.dart` computed
`AppealModel.validateResponse(...)` and used it only to enable the button. The
comment beside that button says the helper text explains why it is disabled;
nothing rendered it. An administrator two words into an answer saw a dead
button and no reason for it — the case `_RejectionReasonDialog` handles by
counting the shortfall down.

**Fixed**: the problem is now the field's `helperText`.

## F6 — the checkout points slider could land off a whole-taka block

**Severity: low, display only. No money was ever wrong.**

The slider's comment claimed "one notch per whole taka, so the slider cannot
land on a figure the policy would round away underneath the buyer". True only
while the cap is at most a hundred taka's worth of points, because
`divisions` is clamped to 100. Above that a notch is `cap / 100` points, which
need not be a multiple of `pointsPerTaka` — so the buyer released the thumb on
347 points, `applyRedemption` floored it to 340, and the label read 340 while
the thumb sat somewhere else.

**Fixed** by rounding down to a whole-taka block in `onChanged` rather than
relying on the notch spacing, which makes the claim true at any cap. The
arithmetic that charges the buyer was already correct on both sides; this only
makes the control agree with the figure it reports.

## F7 — `approveDisposal` read the clock twice for one decision

**Severity: very low. Hardening, not a live defect.**

`server/src/award.js` called `policyModule.dayKey(new Date())` once to compose
the `dailyCaps` document id and again to write the `dayKey` field into it. Two
readings straddling 00:00 UTC would file a counter under one day and stamp it
with another — the exact pair anyone auditing the cap would compare. The
`lockouts` write took a third reading.

**Fixed**: one `decidedAt` for the whole decision. No test, because reproducing
it needs an injectable clock the module does not have and the counter itself is
already covered.

## Considered and deliberately not changed

- **`isApprovable` in `decide.js` is exported, tested and called by nothing.**
  The blocking daily cap it describes is enforced inside `approveDisposal`,
  which is the right place, so the function is documentation with tests rather
  than dead weight. Removing a tested export is a decision about the module's
  API, not a bug fix. Worth noting that the admin queue has no way to know a
  submission is un-approvable until the 409 comes back, if that is ever worth
  surfacing.

- **`AdminWorkloadService` caps its day query at 250 documents before filtering
  by administrator client-side.** On a day with more than 250 decisions across
  all administrators, one administrator's later work stops being counted. The
  code says this outright and the alternative is four composite indexes for a
  vanity counter. Left as documented.

- **`prototypePaymentReference` upper-cases the id it derives the suffix from**,
  so two Firestore ids differing only in case would produce the same `SIM-`
  reference. These are simulation labels that nothing looks up. Left alone.

- **`searchTokensFor` adds the category token last**, so a listing with thirty
  tokens from its title and tags loses it and stops being findable by category
  name. The category *filter* is a separate equality query and is unaffected.
  Not worth reordering against the risk of changing what existing documents
  would index to.

- **The name fields did not get a `maxLength`.** The validator now reports the
  ceiling, which fixes the failure; a character counter on a name field is
  noise.

## Things I checked that turned out to be fine

Recorded so the next audit does not spend the time again.

- **`dart:io` imported by eight files in a web-targeted app.** It compiles —
  verified with `flutter build web`. The `on SocketException` clauses those
  imports exist for are also not the inconsistency they look like:
  `package:http`'s `_ClientSocketException extends ClientException implements
  SocketException`, so the three services that catch only `ClientException`
  produce the same `unreachableServerMessage` as the five that catch both.

- **`averageHash` packing 64 bits into 16 hex nibbles** — correct.
- **`isoWeekKey` at year boundaries** — `floor(days / 7) + 1` is right for every
  first-Thursday offset, and the Dart and JS copies agree.
- **`allocateDiscount`'s restart loop** — cannot spin, because `discount < total`
  and every integer subtotal leaves `shares[i] < subtotals[i]` headroom.
- **Per-order `pointsApplied` summing to the checkout total** — exact, because
  `applyRedemption` has already floored to a whole-taka multiple.
- **Donation idempotency keys being reused for a genuine second donation of the
  same amount** — `resetDraft()` on the success screen's "Donate again" clears
  them.
- **The registration rollback** — `signUp` deletes the Auth account when the
  profile write fails, so a half-registered account is not left behind.
